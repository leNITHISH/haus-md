# Haus MD

A *House, M.D.* appreciation project — and an excuse to learn the fundamentals
of data engineering with [DuckDB](https://duckdb.org/).

The idea: pull the show's data out of the full IMDb dataset dump and build up
a small local warehouse (`haus.duckdb`), learning DuckDB's SQL dialect and
its `read_csv` ingestion options along the way — then run some real analysis
on top of it.

**Status: pipeline built, analysis in progress.** See
[`notes/progress.md`](notes/progress.md) for exactly where things were left
off and what to pick up next.

## Data source

The raw files are the official IMDb non-commercial datasets
(`title.basics.tsv.gz`, `title.episode.tsv.gz`, `title.ratings.tsv.gz`) from
https://datasets.imdbws.com/. They're large (~280 MB total) and gitignored,
so they aren't committed — download them yourself and drop them in `data/`.

Schema and sample rows for each file are in
[`notes/datasets.md`](notes/datasets.md).

## Setup

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

mkdir -p data
# download title.basics.tsv.gz, title.episode.tsv.gz, title.ratings.tsv.gz
# from https://datasets.imdbws.com/ into data/

python3 explore.py    # builds haus.duckdb + all tables, prints house_rolling
python3 findings.py   # runs the analysis queries, prints each result
```

`explore.py` connects to (and creates, if missing) `haus.duckdb` in the repo
root. Every table uses `CREATE TABLE IF NOT EXISTS`, so rerunning the script
is cheap — it won't re-scan the raw `.tsv.gz` files for any table that's
already built.

## Pipeline

Working title-by-title, filtered down from the full IMDb dump to just
*House, M.D.* (`tt0412142`, `startYear = 2004`):

1. **`house_basics`** — the show's own row from `title.basics`.
2. **`house_episodes`** — all 177 episodes whose `parentTconst` matches the
   show, pulled from `title.episode`.
3. **`house_ratings`** — ratings for those same 177 episode `tconst`s,
   pulled from `title.ratings`.
4. **`house_full`** — `house_episodes` joined with `house_ratings`, one row
   per episode, ordered by season/episode (true watch order).
5. **`house_rolling`** — `house_full` plus a 5-episode rolling average of
   `averageRating`, to smooth out noise and spot rating arcs over time.

Each step was built by first `DESCRIBE`-ing the raw CSV to check DuckDB's
inferred schema (catching a couple of real bugs along the way — see
Learnings below), then `CREATE TABLE ... AS SELECT` to materialize the
filtered/joined slice.

## Findings so far

Full queries and write-ups in [`findings.py`](findings.py). Short version:

- **Early vs. late season rating — take 1 (flawed):** a quick flat cutoff
  (`episodeNumber > 15` = "late") suggested late-season episodes rate
  noticeably higher (8.52 vs 8.27). But the split was badly uneven
  (120 early vs 57 late episodes) — a hint the cutoff itself was biased,
  since seasons have different episode counts (~20–24).
- **Early vs. late season rating — take 2 (fixed):** redefined "late" as
  "past the midpoint of *that specific* season" using a window function
  (`MAX(episodeNumber) OVER (PARTITION BY seasonNumber)`). With a fair,
  even split (87 vs 90 episodes), the gap mostly disappeared (8.40 vs
  8.29). Lesson: the first result was largely a measurement artifact, not
  a real effect — worth remembering before trusting any "obvious" first
  result.
- **Data quality quirk:** the series finale's `numVotes` (239) is way out
  of line with every other episode (2,700–9,000+), and its `tconst` is
  numerically much higher than the rest — usually a sign an IMDb entry was
  added long after the fact. Likely a re-tagged/duplicate entry splitting
  votes from an "original" finale row. Flagged, not yet resolved.
- **Rolling average:** built (`house_rolling`), not yet plotted. Next step
  is graphing it to actually look for arcs — e.g. the Season 4 finale
  ("Amber" arc) — visually instead of just scanning numbers.
